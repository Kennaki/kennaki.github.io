NATIVE SECURITY · iOS

接管移动安全 SDK 后的工程化重建

从检测逻辑到持续复检、误报治理和可靠告警。

问题不止是缺少检测项

供应商停止支持后，SDK 仍需应对系统变化、运行期行为及宿主接入问题。我利用 AI 辅助构建增强逻辑，同时把可验证性和宿主稳定性作为交付标准：检测器发现异常只是第一步，证据、调度和上报都必须说得清楚。

分层组织检测能力

上层负责策略、生命周期和检测编排，Objective-C 检测器提供统一结果，C/C++ 层处理需要接近原生系统的数据。检测覆盖越狱、调试、注入、Hook 与网络环境风险。不同检测信号有不同强度，不能因为出现一个弱信号就给正常设备定性。

从符号指针到现代链接结构

传统的导入槽检查不能自动覆盖所有现代 Mach-O 结构。我扩展 Chained Fixups 路径，结合原始导入信息和运行时目标做交叉判断，并处理指针认证相关差异。Runtime 层则检查关键方法 IMP 的来源。这些方法各有覆盖范围，需要真实样本与正常样本共同验证。

运行期需要新的调度方式

启动时完成一次扫描并不足以覆盖后附加等运行期变化。持续全量扫描又会给宿主带来压力。因此把初始化、常规复检、前后台变化和切网触发统一到串行调度中，合并重复触发、错开检查，并在恢复前台时补查到期项目。性能改善需要测量，不能由调度设计直接推导百分比。

让告警能被运维人员理解

将检测结果收敛为实际命中的证据，减少重复描述和不必要诊断数据。告警缓存设置容量与期限，按目标保留投递状态和重试信息。客户端入队成功与服务端最终入库是两个验证阶段，分别检查才能发现链路问题。

用正反例检验检测器

测试不仅包括越狱或注入样本，也包括正常设备、撤销异常状态后的恢复及再次触发。对于证书异常、注入发现和实际阻断，使用各自的验收口径。历史试验能力与当前支持能力分开管理，避免把所有曾写过的检测都当成现行功能。

我的贡献与沉淀

接管并推进 iOS 安全能力增强、运行期调度和稳定性整改，结合 AI 生成实现与人工排障，形成可复现的自测步骤和证据记录。公开复盘聚焦工程取舍，不披露内部策略、检测特征表或客户环境。

Swift 与 SwiftUI 宿主工程

使用 Swift、SwiftUI 开发安全监测壳子工程，集成原生检测 SDK，在真实设备上核对检测结果与应用生命周期行为。

Rebuilding a mobile runtime security SDK

After vendor support ended, I used AI-assisted development to rebuild and extend iOS detection logic, then focused on runtime scheduling, real-device validation, false positives and reliable event delivery. I also built the security-monitoring host app with Swift and SwiftUI to integrate the native SDK and validate behavior on real devices.
