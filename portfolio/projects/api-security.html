用 AI 从零搭建 API 安全分析链路

从 Mac mini 上的验证环境，到隔离内网中的数据、规则与 Web 展示。

角色：单人全栈开发与资源协调技术：Java · Flink · Zeek · Kafka · ES范围：分析链路新建 + Web 接管改造

业务流量→Zeek→Kafka→Flink→Elasticsearch→Web

从哪里开始

原有系统依赖供应商的数据查询接口。我需要让采集、分析和展示链路能够自主维护，并把 API 资产、风险和敏感数据变成可查询、可解释的信息。Flink 分析工程从零建立，Web 则在既有 Spring MVC 工程上接管改造。整个过程由我一人使用 Claude Code、Codex 推进，并协调环境与部署资源。

三周交付与效率提升

原预计约半年完成的 API 监测 Flink 项目，实际三周交付。通过 Claude Code、Codex 推进编码、联调与文档整理，实现十倍以上的编码效率提升；需求拆解、技术取舍、验证及部署由我负责。

先让数据真正走通

我从 Mac mini 创建虚拟机和验证环境开始，部署 Zeek、Kafka 及相关组件。Zeek 脚本补充请求头和 Body 采集，Java 映射层处理字段名称、编码和业务格式。随后把多个分析作业的结果写入 Elasticsearch，再对接 Web 查询。这里处理的是可观测的 HTTP 流量，不把旁路采集等同于直接解密任意 HTTPS。

明细与资产使用不同的数据模型

原始访问记录适合逐条追踪，资产页需要每个 API 一行的汇总。我把 API、Host、Method 作为资产维度，用滚动窗口汇总后更新资产索引，保存首次与最近访问、累计量等信息。风险和敏感数据通过查询关联补充，避免把流水列表硬拼成资产视图。

把旧页面接到新的查询链路

新增 ES 查询服务替换供应商黑盒接口，适配分页、聚合和历史前端字段；新增资产页面，随后完善态势图表、筛选与 CSV 导出。排查时需要同时理解浏览器请求、Action 参数、ES mapping 与数据类型，才能区分“没有数据”和“查错了数据”。

有状态检测与设备补全

在基础规则之外，引入按 token、设备和 IP 分组的滚动窗口，识别跨设备使用或短时关联变化。H5 请求通过设备标识关联约十万条记录的设备库，使用 LRU 缓存减少重复查询；补全设备信息时仍保留原本的 H5 分类。记录规模是关联库规模，不代表实时吞吐。

一次请求为什么被统计两遍

多个分析作业会为同一请求写入不同类型文档。如果图表直接统计所有文档，访问量就会翻倍。我回到指标定义，限定访问统计所使用的文档类型；时间趋势则分别处理时区、聚合粒度和缺失时间桶。修复的重点是统一数据语义。

代码改了 为什么环境没有变化

部署过程中，源码、JAR、镜像和实际运行实例曾出现版本不一致。我逐层核对构建产物、镜像与 Pod 的 Image ID，定位旧镜像缓存，同时修正多模块构建和依赖版本。离线依赖与跨架构部署也需要单独验证，不能以本机运行成功代替内网验收。

AI 协作中的人工责任

AI 承担大量实现工作，我负责拆解任务、核对字段契约、选择验证路径并修正环境推断。交接文档持续记录已证实根因、失败假设和待办。代码看似正确时，仍要检查实际运行产物及中间件状态；无法证实的问题保留未定结论。

交付与边界

完成采集、实时分析、资产聚合、Web 展示及内网部署链路，并沉淀测试脚本和交接材料。该实践不以未经测量的吞吐倍数或“纯 AI 无需人工”作为成果，也不将部署配置等同于已经验证的 exactly-once 与无损状态恢复。
